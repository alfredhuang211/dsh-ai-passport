## 1. 决策速览

| # | 决策 | 结论 | 理由 |
| --- | --- | --- | --- |
| D1 | 协议版本 | **升到 v2**（`task.state` → `session.list/session.detail/session.done`；`session.select`；`voice.*`/`approve.req` 带 handle） | 设备端现在**没有会话概念**，纯增量消息无法表达列表；两端本轮同版发布，v2 比「v1 里塞隐性结构」更干净 |
| D2 | 会话标识 | 主机分配**稳定短 handle**（`01`–`08`），设备只认 handle | 不把 DSH 的 `sessionId` 放进 BLE 载荷（长度/隐私/格式都不可控）；排序变化时 handle 不变，避免"选错会话" |
| D3 | 状态的表达 | **形状图标 + 颜色**，不显示状态文字：绿=运行中、黄=等待你处理、红=出错/中断、灰=空闲；文字只保留会话名 | 用户要求"用 icon/颜色表示状态、尽量少文字"；形状差异同时照顾色弱用户 |
| D4 | 设备菜单根页 | **主页 = 会话列表**；设置页=「上长按」，余额页=「下长按」，会话页=「按住确定」说话 | 覆盖 5 个动作、故意留空 1 个，且保留现有固件已有的「上长按=设置、下长按=余额」肌肉记忆 |
| D5 | 语音发送 | 松手 → 识别 → **结果卡（发送/重说/放弃）**，单击确定发送到该会话；配置项可开「自动发送」默认关 | 保留"看一眼再发"（识别必然有误），同时把"发送"做成一次按键；符合 R4 的"说话来发送" |
| D6 | 桌面设置页 | `settings.section`（设置侧栏独立一页，id=`ai-passport`，order≈30） | 用户明确选择"设置侧栏独立一页"；DSH 有第三方先例（dshmarket） |
| D7 | 会话旁指示 | 从 `conversation.input.activity` 挪到 **list 槽**（`conversation.session.header.utilities`） | activity 是 single 槽，现有挂件与官方语音输入同优先级注册 → 麦克风插件激活失败（今日 10:46 崩溃日志实证） |
| D8 | 设置持久化 | 插件自有 `~/.dsh/dsh-ai-passport.settings.json` + 现有 HTTP `/dsh-passport/action` | 避免 `ctx.settings.update()` 触发 Loader 热重载 → BLE 链路重建（本项目最脆的一环）；`transport`/`autoConnect` 等启动项只读展示 |
| D9 | 旧固件兼容 | 主机按协商版本自适应：v2 发 `session.*`；v1 继续发旧的 `task.state` 聚合态 | 用户手上还有旧固件；升级期不能"刷一半就瞎" |
| D10 | 声音设计 | 待审批=**QQ 原版咳嗽采样**（本地构建、不入库，缺采样回落合成）；追问=采样单咳；会话结束=**BP 机 4 连响**（合成） | 用户试听后确认"原版更好"；采样+合成双路径兼顾听感、体积与版权 |
| D11 | 会话列表排序 | **按最近更新时间倒序，最新在最上**（不再按"等待人工 > 运行中"分组排序） | 用户确认；排序稳定可预期，待处理事项由黄色图标与审批弹窗提醒 |

## 3. 协议 v2

### 3.1 版本与协商

- `AP_PROTOCOL_VERSION`（固件 `app_proto.h`）与 `PROTOCOL_VERSION`（插件 `lib/protocol/constants.js`）同步 **1 → 2**；parity 测试锁死。
- `hello.caps` 增加能力位 `CAP_SESSION_LIST`（v2 设备置 1）。
- 协商取双方较小值：
  - 协商 ≥2 → 走 §3.2 新消息；
  - 协商 =1（旧固件）→ 主机只发旧 `task.state` 聚合态，新消息一律不发；
  - **新固件 + 旧主机（v1）**：设备降级显示单一聚合态（复用旧四态渲染），并提示「主机插件过旧，建议升级」；不静默空白；
  - 设备收到 v2 主机但自身 v1 时，本来就会因版本不一致丢弃（现有行为），**不能静默**：设备屏提示"协议版本过旧，请升级固件"。

### 3.2 消息表

**主机 → 设备（新增/修改）**

| type | 载荷（全部扁平标量） | 说明 |
| --- | --- | --- |
| `session.list` | `{n, handles, titles, states, unread, sel}` | 会话快照（全量替换）；`handles="01\|02"`、`titles="重构登录\|修复乱码"`、`states="running\|waiting"`、`unread="0\|1"`、`sel="02"`；`n` 条数；`sel` 空串=未选 |
| `session.detail` | `{h, title, state, step, stepTotal, tool, elapsedMs, summary}` | 设备进入/刷新某会话时下发；`stepTotal` 未知时省略（设备显示不确定态）；`summary` ≤120 UTF-8 字节 |
| `session.done` | `{h, title, result, durationMs}` | turn 结束提醒；`result=completed\|error\|aborted\|interrupted` → 横幅文案/提示音/未读点 |
| `approve.req`（改） | `{id, summary, risk, timeoutMs, h, title}` | 追加会话 handle + 标题（≤16 字） |
| `voice.result`（改） | `{resultId, text, h, audioSeconds}` | 追加目标会话 handle |
| `voice.error`（改） | `{message, h}` | 同上 |
| `question.req`（改） | 现有字段 + `{h, title}` | 追问/计划弹窗也显示「会话：<标题>」，与审批一致 |
| `config`（改） | `{soundEnabled, backlightPulse, maskTitles, detailSummary, detailElapsed, time?}` | 设备显示开关；`time` 为可选 epoch 秒（无时钟源时省略）；设备不持久化，唯一事实源在主机 |
| `sound.test`（新） | `{kind}` | 桌面设置页「试听」→ 设备播放对应提示音（`approve\|completed\|error\|decided\|pair_ok\|pair_fail\|low_battery`） |
| `task.state`（仅 v1 兼容） | `{state, title}` | v2 设备不再收发 |

**设备 → 主机（新增/修改）**

| type | 载荷 | 说明 |
| --- | --- | --- |
| `session.select` | `{h}` | 设备进入/切换到会话 h（同时清除该会话未读） |
| `session.detail.req` | `{h}` | 刷新当前会话详情（会话页下长按） |
| `session.list.req` | `{}` | 列表为空时每 5s 自动请求（§6.7），不占用按键；主机回 `session.list` |
| `voice.begin` / `voice.end`（改） | `{sessionId, target, sampleRate, bits, channels, codec, durationMs, maxRms}` | `sessionId` 保持音频流序号语义不变；**新增 `target`** = 目标会话 handle |
| `voice.action`（改） | `{resultId, mode, target}` | `mode=send\|redo\|discard`；`fill` 保留但 v2 设备不再使用（见 §4.3） |
| `approve`（不变） | `{id, decision}` | 审批仍只回 id |
| `settings.set`（新） | `{soundEnabled?, maskTitles?}`（可选字段） | 设备设置页改「提示音/标题打码」→ 主机（唯一事实源）→ 主机回 `config` 确认 |
| `ping` / `hello` / `pair.*` | 不变 | — |

**删除（v2）**：`task.state` 对 v2 设备不再发送。

### 3.3 扁平编码规则（设备解析器硬约束）

设备 `ap_json_*` 不解析嵌套数组/布尔，因此：

1. 列表字段一律用 `|` 拼成一个字符串；长度以 `n` 为准。
2. 标题转义：`|` → `¦`，`\` → `╲`，换行/控制符 → 空格；按**UTF-8 字节**截断到 40 字节（在字符边界截，不切半个汉字）。
3. 标题打码（`maskTitles`）在主机侧完成后才编码：`会话 1 / 会话 2 …`。
4. 排序与上限：最多 **8** 条（`maxSessions`），排除 `origin='subagent'` 与 `blank`（除非 running）；排序 = **`updatedAt` 倒序（最新在最上）**；`updatedAt` 相同则按 handle 升序稳定排序。
5. 体积核算（最坏 8 条）：handle 8×3 + title 8×41 + state 8×8 + unread 8×2 + 分隔符 ≈ **450 B** ≪ 2048 B 上限，单条消息即可，不分片。
6. **可靠性**：所有新业务消息走控制通道，**要求 ACK**（`ACK_REQ` 位）；`ack/nack/pong` 不回 ACK。超时 400ms、重传 3 次（沿用现有链路）。
7. **顺序**：同一事件先发 `session.list` 再发 `session.done`（BLE GATT 通知同序）；设备收到 `session.done` 时若列表尚未包含该 handle，暂存 1s 等列表，超时丢弃。
8. **配对门控**：未配对连接上来的业务消息一律不回、回 `pair.required`；`session.*` 与 `voice.*`/`approve.req` 同属门控范围。

### 3.4 时序

**连接同步**

```
设备 hello{caps,ver=2} ──► 主机
主机 hello.ack{ver=2} ◄──
主机 session.list{...} ◄──  （链路 READY 即推一次全量）
主机 session.detail{h=sel} ◄──（若上次选择仍有效）
```

**选择会话**

```
设备：会话列表 上/下选中 → 短按确定
设备 session.select{h=03} ──► 主机
主机：sel=03，清该会话未读 → 回 session.list（sel 更新）
主机：session.detail{h=03} ──► 设备（会话页数据）
```

**语音发送到指定会话**

```
设备会话页：按住确定（按下即录）→ 松手
设备 voice.begin{target=03,…} ──► 主机
设备 voice.end{target=03,durationMs} ──► 主机
主机：转写 → voice.result{resultId,text,h=03} ──► 设备
设备：结果卡（发送/重说/放弃）
设备 voice.action{resultId,mode=send,target=03} ──► 主机
主机：sessionController.prompt({sessionId=handle03 对应会话, content:[{type:'text',text}]}, AbortSignal.timeout(15s))
主机：toast{text:"已发送到「<标题>」"} ──► 设备
```

**审批（保持现有竞速模型，补会话上下文）**

```
主机 approval/request 到达 → 设备与电脑卡片同时显示（先答者胜）
主机 approve.req{id,summary,risk,timeoutMs,h,title} ──► 设备
设备：审批弹窗（会话：<title>）→ 上/下选择 → 单击确定
设备 approve{id,decision} ──► 主机 → approve.result 收起弹窗
```

**完成提醒**

```
主机 session/event turn/end → 状态=idle/error，未读=1
主机 session.list（未读位）＋ session.done{h,title,result,durationMs} ──► 设备
设备：横幅 3s + 区分提示音 + 列表未读点；进入该会话后清除
```

## 4. 主机插件改造

### 4.1 `SessionDomain`（取代 `StateDomain`）

文件：`lib/bridge/state.js` → 重写为 `lib/bridge/sessions.js`（旧的 `state.js` 删除；v1 兼容聚合改为在 `sessions.js` 内维护 `#legacyState()`，避免两份会话表漂移）。

**数据模型**

| 字段 | 来源 |
| --- | --- |
| `sessionId` | `SessionSummary.sessionId` / `api-session/*` |
| `title` | `summary.projections.values.title`；实时更新用 `session/event` 的 `session/title` 事件（`event.data.title`） |
| `running` | `api-session/status(id, running)` |
| `state` | 映射规则见下 |
| `unread` | `turn/end` 且设备**未选中**该会话时置 1；设备 `session.select` 该会话时清除。桌面端聚焦不自动清除（见 §4.7） |
| `endedReason` | `session/event` 的 `turn/end` → `event.data.reason.kind`（`completed/aborted/blocked/error/max-tokens/interrupted/forked`） |
| `updatedAt` | `api-session/activity` 与 `SessionSummary.updatedAt` |
| `step/tool/elapsed/summary` | 详情页数据：`turn/start`+工具事件累计；`session.follow()` 按需补最近一条助手输出（限流） |

**状态映射**

| 内部状态 | 判定 | 设备色 |
| --- | --- | --- |
| `waiting` | 该会话有挂起审批/追问（审批域/追问域回调告知） | 黄 |
| `running` | `running=true` | 绿 |
| `error` | `endedReason ∈ {error, blocked}` | 红 |
| `aborted` | `endedReason ∈ {aborted, interrupted}` | 红（文案"已中断"） |
| `idle` | 其余 | 灰 |

**handle 表生命周期**：每次链路建立（`hello.ack`）重新分配/校准 handle 表；断链即作废；设备重连后清空选中（C12）。同一连接内排序变化不改 handle。

**推送策略**

- 变更合并：250ms 合并窗口；快照 hash 不变不推。
- 录音期间抑制：`voice.begin` → `voice.end` 期间不推 `session.list`（沿用现有 `deviceRecording` 守卫，避免"说话时列表跳"）。
- 去重/补推：链路 READY、断线重连、`session.select` 后强制全量。
- **排序**：快照按 `updatedAt` 倒序；`updatedAt` 取该会话最近一次**有意义的**事件时间（turn/start、turn/end、用户消息/activity、标题变更、审批/追问挂起），不取工具调用的高频时间 —— 否则列表会每秒重排。
- **重排与选中**：重排后 handle 不变，设备按 handle 保持选中；若被选中的行位置变化，设备只移动高亮，不切换当前会话。录音/审批弹窗期间列表推送被抑制，不会在用户操作时跳行。
- 未读与「已完成」：不再需要 8 秒全局回落；改按会话：`turn/end` 后该会话状态保持到下次变化，未读点常驻，进入即清。

**v1 兼容聚合器**：若协商版本=1，`#legacyState()` 按旧规则聚合（待审批 > 运行中 > 已完成停留 8s > 空闲）并下发 `task.state`；v2 设备同时只走 `session.*`。两套输出共用同一份会话表。

### 4.2 审批域：加会话上下文

- `approval/request` 的 `req` **没有** `sessionId`：用 `req.agent?.id ?? req.agent?.session?.id` 推导。
- 标题：`ctx.get('sessionTitle')?.get(req.agent.session)?.title`；兜底查 `sessionController.list()` 的 `projections.values.title`。
- 下发 `approve.req` 追加 `{h: handleOf(sessionId), title: clamp(title,16)}`；标题为空时用「另一个会话」兜底（不让弹窗出现空行）。
- 竞速模型（`prepend` + 电脑卡片并行 + 先答者胜）**保持不动**；只加字段与设备端展示。

### 4.3 语音域：定向发送

- `voice.begin/end` 的 `target` → 解析为 `sessionId`；解析顺序：handle 表 → 设备选中会话 → `running` 会话 → 最近 `updatedAt` 非空会话（现有兜底逻辑）。
- `voice.action{mode:'send'}` → 直接 `sessionController.prompt` 到解析出的会话：
  ```js
  await controller.prompt(
    { requestId: `passport-voice-${Date.now().toString(36)}`,
      sessionId, mode: 'queue',
      content: [{ type: 'text', text }] },
    AbortSignal.timeout(15_000),   // ★ 必传（见 §8 P0）
  )
  ```
- `mode:'fill'`：v2 设备只会发 `send/redo/discard`；`fill` 仅用于**旧固件（v1）**兼容。S4 删除了输入框旁挂件（`conversation.input.activity`），已无 `voice.take` 消费者，因此 send/fill 都改为「先登记 pending，2.5s 无人认领即定向直发」，避免旧固件的「填入」永远挂起。
- `voice.result` 带 `h`，设备结果卡显示目标会话标题。

### 4.4 面板/动作/快照扩展

`runtime.dispatch` 新增：

| action | 载荷 | 作用 |
| --- | --- | --- |
| `session.focus` | `{sessionId}` | 桌面客户端上报**窗口聚焦会话**（`desktopFocusedSessionId`；用于指示器文案与旧固件 fill 判定；与设备选中 `deviceSelectedSessionId` 是两个概念） |
| `session.select` | `{h}` | 面板/调试用，模拟设备选会话 |
| `settings.get` | `{}` | 读运行时可改设置 |
| `settings.set` | `{patch}` | 写设置并立即生效 |

`snapshot()` 增加 `sessions[]`、`selectedHandle`、`deviceSelectedSessionId`、`desktopFocusedSessionId`、`settings`（供设置页与状态指示使用）。

> 命名约定：**deviceSelected** = 设备上选中的会话；**desktopFocused** = 某个桌面窗口当前打开的会话。二者可能不同，指示器要分别展示。

### 4.5 设置存储

- 文件：`~/.dsh/dsh-ai-passport.settings.json`（与 pairing store 同模式，原子写）。
- 可写项（运行时可改）：`maskTitles`、`notify.sound`、`notify.backlightPulse`、`detailSummary`（默认 true）、`detailElapsed`（默认 true）、`voice.autoSend`（默认 false）、`approval.enabled`、`maxSessions`（1–8）、`listRefreshMs`。
- 只读展示（启动期配置，改动需改 `cordis.patch.yml` + 重启）：`transport`、`autoConnect`、`targetDeviceId`、`voice.providerId`。设置页明示"需重启生效"。
- 生效方式：写入后由 `SessionDomain`/`ApprovalDomain`/`VoiceDomain` 直接读 store，不触发 Loader 重载。

### 4.6 多审批 / 多追问的排队策略

现状是"一个审批一个弹窗"，但多会话并行时可能**同时**出现多个 `approval/request`，或审批与追问同时到达。方案：

| 规则 | 内容 |
| --- | --- |
| 设备一次只显示一个模态页 | 按**到达顺序**排队；当前页关闭（作答/放弃/撤销）后立即弹下一个 |
| 优先级 | 审批 > 追问/计划（与 §6.4 一致）；同类型按到达顺序 |
| 声音 | 每个新请求到达都按 §6.8 响一次；但同一音型 3s 内去重（避免连响成噪音） |
| 角标 | 列表页/状态条显示「待审批 N」小角标（N>1 时才显示，用数字而非文字） |
| 超时/断链 | 保持 §4.2 竞速模型：设备支线退出后电脑卡片继续等；排队项不受影响 |
| 电脑先答 | 主机推 `approve.result`/`question.done` → 设备收起当前页并弹队列下一项 |

> 为什么不合并成一个"批量审批"页：每个请求属于不同会话、风险不同，合并会诱导用户一次放行多个高风险操作。

### 4.7 隐私、持久化与数据边界

## 6. 设备固件：菜单层级与页面（R5 重点）

### 6.1 菜单层级

```
[上电]
 └─ 配对页（未配对时）
      ├─ 电脑输码成功 ──► 会话列表
      └─ 长按确定（跳过）──► 会话列表（离线态：列表区显示"未配对"）

会话列表（主页，默认）
 ├─ 上短按：选中上移
 ├─ 下短按：选中下移
 ├─ 上长按 ──► 设置页            （沿用现有「上长按=设置」）
 ├─ 下长按 ──► 余额页            （沿用现有「下长按=余额」）
 ├─ 确定短按：进入选中会话 ──► 会话页
 └─ 确定长按：不使用（留空，避免与"进入"误触）

会话页（某会话）
 ├─ 上短按：上一个会话（原地切换）
 ├─ 下短按：下一个会话
 ├─ 上长按：返回列表
 ├─ 下长按：刷新详情（session.detail.req）
 ├─ 确定短按：无业务动作（<0.5s 误触，录音丢弃）
 └─ 确定长按：按住说话 ── 松手 ──► 语音结果卡

设置页（来源：列表页上长按）
 ├─ 上短按：上一项
 ├─ 下短按：下一项
 ├─ 确定短按：进入 / 切换 / 确认（「设备信息」进入子页）
 └─ 上长按：返回列表

余额页：确定（任意）= 返回列表；其余不使用
配对页：长按确定 = 跳过（离线可用）；其余不响应

覆盖层（不进菜单栈）：
 模态（消费按键）：审批弹窗 > 追问/计划评审 > 语音结果卡
 非模态（不消费按键）：完成横幅、toast
```

**为什么这样分层**

- 主页直接是会话列表：用户要的是"现在有哪几个任务、哪个要我管"，多一层菜单只会增加按键次数。
- 设置/余额沿用现有「上长按/下长按」入口，不破坏已有肌肉记忆；两者都是低频页，不占主页按键。
- 会话页把动作分给「上/下切会话、上长返回、下长刷新、确定按住说话」5 个；**列表页的确定长按故意留空**，避免与"进入会话"在同一键上按时长误触。
- 全设备 PTT 统一为「按住即录、松手结束」（与现有主页/追问语音页一致），不做"长按若干毫秒才开始录"的第二套手势。
- 覆盖层分两类：**模态**（审批 > 追问 > 结果卡，消费按键、同时最多一个）与**非模态**（完成横幅、toast，不消费按键）；新页面**不得**打断模态覆盖层。

### 6.2 按键映射总表（3 键 × 短/长 = 6 动作）

| 页面 \ 动作 | 上短 | 上长 | 下短 | 下长 | 确定短 | 确定长 |
| --- | --- | --- | --- | --- | --- | --- |
| 会话列表（主页） | 选中上移 | 到设置页 | 选中下移 | 到余额页 | 进入会话 | —（留空） |
| 会话页 | 上一会话 | 返回列表 | 下一会话 | 刷新详情 | —（误触丢弃） | **按住说话** |
| 设置页 | 上一项 | 返回列表 | 下一项 | — | 进入/切换/确认 | — |
| 余额页 | — | — | — | — | 返回列表 | 返回列表（任意确定） |
| 配对页 | — | — | — | — | — | 跳过配对 |
| 审批弹窗 | 上一项 | — | 下一项 | — | 确认提交 | 放弃（交回电脑） |
| 追问/计划弹窗 | 上一项 | — | 下一项 | — | 选择/勾选（单选即执行） | 提交整批 |
| 语音结果卡 | 放弃 | — | — | — | 发送到该会话 | 重说 |
| 完成横幅（非模态） | — | — | — | — | — | — |

**确定性约定**

- 长按门限沿用 BSP（500ms）。上/下长按在"用户可能在连滚"的页面上**不安排导航动作**，只安排"到设置/余额"这类低频入口，且松手后不回溯触发短按动作。
- 会话页「确定长按 = 按住说话」是**语义**；实现上按住型手势只能在按下时开始采样（否则会丢掉开头 0.5 秒语音），所以：按下即开始录音、松手结束；短于 0.5s 的误触由主机丢弃（不产生消息、不弹结果卡），等价于"短按无动作"。若将来需要"短按绑定独立动作"，才引入"按下先缓存、满 500ms 转正"（约 +4KB ADPCM 缓冲，需实测 RAM）。
- **模态**覆盖层优先消费按键，未消费的按键**不穿透**到下层页面；**非模态**提示（横幅/toast）不消费按键。

### 6.2.1 按键冲突审查（本轮修掉的 12 处）

| # | 冲突 | 原设计 | 处理 |
| --- | --- | --- | --- |
| C1 | 列表页上/下长按**双重指派**：到顶/到底 vs 设置/余额 | 同键两义 | **去掉"到顶/到底"**：单行布局下 8 行一屏放得下（行高 30），滚动只在调大上限时兜底，快速跳转无必要；长按只做设置/余额 |
| C2 | 列表页"确定长按=按住说话"与"确定短按=进入"同键按时长区分 | 想进入却按久 → 误录音；且列表页没有"当前会话"上下文 | **删除列表页快捷 PTT**，说话只在会话内（符合 R4 原文）；确定长按留空 |
| C3 | 会话页双返回：上长=返回 与 确定短=返回 | 一键两义 | 统一为**上长=返回**；确定短不再绑定返回（改为无业务动作/误触丢弃） |
| C4 | 会话页 PTT 语义"确定长按=说话"与实现"按下即录"混写 | 文档层面读起来像两种手势，易误实现为"等 500ms 再录"→丢开头语音 | 明确：**语义=长按说话**，**实现=按下即采样、松手结束**；<0.5s 丢弃即"短按无动作"（与现有主页/Q_VOICE 一致） |
| C5 | 设置页双返回：上长=返回 与 确定长=返回 | 一键两义 | 只留**上长=返回**；"下长=翻到底"（6 行内无必要）删除 |
| C6 | 余额页双返回：上长=返回 与 确定=返回 | 一键两义 | 只留**确定=返回**（沿用现有固件行为） |
| C7 | 配对页全键不响应 | 电脑端不在时用户被困在配对页 | 新增**长按确定=跳过**，进离线态列表页；电脑输码成功后自动进入 |
| C8 | 录音中审批到达未定义 | 手按在确定上时弹审批 | 审批优先：**立即停录并丢弃** + toast「录音已取消（审批优先）」；松手事件被审批层消费，不二次录音 |
| C9 | 结果卡与审批叠放未定义 | 审批盖住结果卡后，结果卡去留不明 | 审批结束后 **60s 内恢复结果卡**，超时丢弃（防幽灵状态） |
| C10 | 完成横幅是否消费按键未定义 | 若消费，会挡住 3 秒内的切换/说话 | 定为**非模态**：不消费按键、3s 自动收起；不做"确定跳转"（用户上/下选中后进入即可） |
| C11 | 追问页"其他→语音输入页"的手势与新会话页不一致 | 同设备两套 PTT | 统一为"按住即录"（同 C4） |
| C12 | 重连后 handle 失效，设备旧选中未清 | 可能把语音发到错误会话 | 重连后**清空选中、回列表顶部**，等新 `session.list`（§6.7 已补） |

### 6.4 覆盖层优先级（沿用并扩展）

```
模态覆盖层（消费按键）：审批弹窗  >  追问/计划评审  >  语音结果卡
非模态提示（不消费按键）：完成横幅、toast
```

- **模态**覆盖层任何时刻最多一个，新页面/覆盖层必须纳入 `hide_all_panels` 遍历顺序。
- **非模态**提示（完成横幅 3s、toast）只占屏幕局部、不拦截按键：按键直接作用于当前页，避免"横幅挡着不能说话/切换"的新冲突。
- 录音期间：不弹审批之外的任何覆盖层（避免打断）；审批仍可抢占（安全优先），**立即停录并丢弃** + toast「录音已取消（审批优先）」，松手事件由审批层消费，不二次录音。
- 结果卡与审批叠放：审批在上；审批结束后 60s 内恢复结果卡，超时丢弃（防幽灵状态）。
- 新枚举值**必须插在 `AP_SCREEN_SETTINGS` 之前**（`app_screens.c:573-584` 的遍历依赖顺序）。

### 6.6 资源与约束

- 屏幕 240×320，安全区 220×300（外壳圆角遮挡 10px）。
- LVGL 固定池 **64KB**（`sdkconfig.defaults`）：列表行控件**一次性创建、只改文本/颜色**；禁止每次刷新重建。
- 会话表：8 × (handle 3 + title 40 + state 8 + unread 1) ≈ 420B，可接受。
- 中文字体已有 20px/16px 子集（各 3899 字），会话标题直接显示中文；缺字显示方框（不 sanitize）。
- 单消息 ≤2048B、≤16 片；列表单条消息即可。

### 6.7 异常与降级

| 场景 | 设备行为 |
| --- | --- |
| 蓝牙未连接 | 列表页显示"蓝牙未连接"+ 排查建议；不显示过期会话（进离线态清空动态字段） |
| 主机未运行/插件未装 | 同未连接；文案"等待电脑端 AI Passport 插件" |
| 协议版本不匹配 | 明确提示"协议版本不一致（设备 v2 / 主机 v1），请升级另一端"，不静默 |
| 列表为空 | "没有会话" + 操作提示；**自动每 5s 重新请求**（不占用按键，避免与"下长按=余额"冲突） |
| 选中会话消失（被删/归档） | 主机下一份 `session.list` 中 handle 失效 → 设备自动回到列表顶部并清选中；不做隐式切换 |
| 录音中断线 | 丢弃本次录音，toast"连接断开，录音未发送" |
| 审批未到达（丢消息） | 保留现有 40s 兜底回落 idle |
| 会话标题超长/含特殊字符 | 主机截断到 40 UTF-8 字节并转义 `|`；设备只显示 |
| 重连后旧 handle 失效 | 设备**清空选中、回列表顶部**，等新 `session.list`；不保留旧选择（否则语音可能发错会话） |
| 电脑端不在（配对页） | 长按确定可跳过，进离线态列表；列表区提示"未配对"，不卡死 |
| 跳过后电脑端来配对 | 收到 `pair.begin` 时**重新弹配对页**（跳过只跳过当前等待，不是永久关闭配对） |
| 设备离线时任务完成 | 不补响提示音（避免重连后突然响）；未读点由主机保留，重连后随 `session.list` 显示 |
| `session.detail.req` 的 handle 已失效 | 主机回 `toast「会话已关闭」`；设备回列表，不猜测替代会话 |
| 未配对/握手中收到业务消息 | 设备按 `pair.required` 处理，不渲染业务页面 |
| 连接失败原因区分 | 主机 `lastError` 的 `adapter-off` / `permission-denied` / `device-not-found` 映射到设备离线页三行文案（蓝牙关/未授权/找不到设备），不笼统写"未连接" |

### 6.8 声音设计

> 目标：**"需要你处理"用咳嗽声，"会话结束"用 BP 机消息声**，两种声音在嘈杂环境/隔着房间也能区分；
> 沿用固件现有「运行时合成、零 Flash」的做法，只是把"正弦音调表"升级成"波形 + 段序列"。

#### 6.8.1 事件 → 声音映射

| 事件 | 声音 | 波形 / 节奏 | 优先级 | 说明 |
| --- | --- | --- | --- | --- |
| 待审批（`approve.req`） | **咳嗽 ×2** | **原版采样回放**（8k，0.66s）；缺采样时回落合成：f0 390→296Hz 下滑 + 共振峰 ~883/1173Hz | P0 | 最高优先级，可打断低优先级声音 |
| 追问 / 计划待审（`question.req`） | **咳嗽 ×1** | **原版采样前 0.30s**（8k）；缺采样时回落单咳合成（f0 296Hz） | P0 | 与审批同为"要你处理"，用次数区分紧急度 |
| 会话完成（`session.done.result=completed`） | **BP 机消息声** | 正弦 3200Hz，**4 连响**（每响 140ms、间隔 110ms），对齐原版 BB 机 | P1 | 用户指定 |
| 会话出错（`error`） | BP 机变体 | 4 连响 + 尾部 600Hz 低音 200ms（下坠感） | P1 | 与"完成"可辨 |
| 会话中断（`aborted/interrupted`） | BP 机三连响 | 3200Hz ×3（每响 100ms、间隔 120ms） | P1 | 比完成"轻"一档 |
| 设备上已提交/已选择 | 确认滴答 | 正弦上行双音 1200→1500Hz，70ms | P2 | 沿用现有 `ALERT_DECIDED` |
| 语音识别完成（结果卡出现） | 轻提示 | 正弦 1800Hz 60ms（低音量） | P2 | 不打断对话 |
| 语音发送成功 | 短 tick | 2000Hz 40ms | P2 | 结果卡收起时 |
| 语音发送失败 | 低频 buzz | 300Hz 方波 2×80ms | P2 | 配 toast 原因 |
| 配对成功 | 上行三音 | 800→1200→1600Hz 各 90ms | P2 | 一次 |
| 配对失败 | 下行双音 | 1200→700Hz | P2 | 配合剩余次数提示 |
| 连接建立 / 断开 | 轻升调 / 轻降调 | 1000↔1300Hz 150ms | P3 | 可关（默认只连上响，断开不响） |
| 低电量（<15%） | 双低音 | 500Hz 方波 2×120ms | P1 | 每 10 分钟最多一次 |
| 充电插入 | 轻双音 | 800/1200Hz | P3 | 可关 |

#### 6.8.2 波形合成方案（升级 `main/app_alert.c`）

原实现只有"正弦音调表"，做不出咳嗽；BP 机 4 连响用正弦段就能做。方案：

| 波形 | 用途 | 合成方式 |
| --- | --- | --- |
| `HARMONIC`（咳嗽，**回落路径**） | 审批/追问（无采样时） | 声门谐波 + 共振峰：按 f0 给各次谐波分配幅度 `G(k·f0)`，`G(f)=1.0·e^{-((f-1173)/170)²/2} + 0.07·e^{-((f-883)/160)²/2} + 0.22·e^{-((f-585)/140)²/2}`；f0 前段 390Hz、235–255ms 滑到 296Hz；包络用原版实测的 27 个结点（20ms 间隔）；起音加微量气声 |
| `SINE` | BP 机 4 连响、确认滴答、配对、轻提示 | 正弦 + 4–5ms 淡入淡出（原版 BB 机提示音实测为纯音，无谐波） |
| `SQUARE` | 低电量等 | 方波（相位取符号） |

**固件实现要点**

- 咳嗽不做逐样本 `sinf`：启动时按 390Hz / 296Hz 各生成一张 256 点单周期波表（谐波幅度按上式加权），播放时按相位累加查表 + 线性插值；音高切换只换波表。
- BP 机 4 连响 = 4 个正弦段（140ms 响 / 110ms 静音），段序列驱动，零新增缓冲。
- 仍**零 Flash 音频样本**；`s_buf` 12.8KB 不变。
- 音量沿用 `s_volume` + 主机 `soundEnabled`；0 = 静音。

#### 6.8.2.1 原版参考与实测参数（只用于推导参数，不随固件分发）

| 参考 | 来源 | 实测特征 |
| --- | --- | --- |
| QQ「咳咳」（好友上线） | GitHub `Melinda-Mel/qq-chime-skill` 的 `qq-ke-ke.mp3` | 0.67s；浊音，f0 前段 ~390Hz → 后段 ~296Hz；能量 91% 集中在 1–1.5kHz（共振峰 ~883/1173Hz）；双脉冲包络 |
| BP 机提示音 | bilibili `BV1KR4y1K72A`《BB机的几种提示音》12.20–13.14s | 0.9s；4 连响，每响 ~140ms，间隔 100–120ms；**纯正弦 3200Hz**（谐波几乎为零） |

我们的合成结果与参考对比（同一套分析）：

| 指标 | 原版咳嗽 | 合成咳嗽 |
| --- | --- | --- |
| 能量 1–1.5kHz 占比 | 91.1% | 89.2% |
| 能量 300–1000Hz 占比 | 7.9% | 10.2% |
| 10ms 包络相关 | — | **0.987** |

> 版权：参考音频**不进仓库、不进 Release**；发布版固件只用合成参数。本地构建可选择放入采样（§6.8.2.2），此时音色为原版采样。

#### 6.8.2.2 方案 B：样本回放（咳嗽采用）

合成版在频谱/包络上已很接近原版（§6.8.2.1），但试听确认**原版更有"人味"**（真人咳嗽的噪声起始、共振峰过渡、微抖动都是合成难以复刻的）。因此咳嗽改为**采样回放**：

| 项 | 做法 |
| --- | --- |
| 采样来源 | 原版 QQ 咳嗽（48kHz 立体声 mp3）→ **8k** 单声道 PCM16（16k 备选）；去首尾静音、归一化到 -1dBFS、首尾 3ms 淡入淡出 |
| 体积 | **采用 8k：0.66s ≈ 10.4 KB**；16k 版 20.8 KB 作为备选（C3 app 槽 1.8MB，当前基线 ~1.5MB，两者都够） |
| 单咳（追问） | 取采样前 ~0.30s + 淡出；或单独生成 `alert_cough_once.h` |
| 转换工具 | `tools/make-sound-asset.mjs`：WAV → C 头文件（`*_SAMPLE_RATE/_SAMPLE_COUNT/_PCM[]`），支持 `--rate/--gain/--trim` |
| 固件集成 | `main/app_alert.c` 用 `#if __has_include("sound_assets/alert_cough.h")` 决定走采样；头文件缺失时回落 §6.8.2 的合成咳嗽 —— **仓库里不含音频，照样能构建** |
| 播放 | 播放前 `bsp_audio_set_format(8000,16,1)` → `bsp_audio_write(PCM)`；**提示音任务需按音型切换采样率**（采样 8k / 合成音 16k），播完恢复；不新增解码器 |

**版权与仓库卫生（重要）**

- QQ 咳嗽音效版权归腾讯；即使某 GitHub 仓库以 MIT 分发该 mp3，**原始音频版权不随之转移**。
- 因此：采样文件、生成的 C 头文件一律放 `sound-assets/`（已加入 `.gitignore`），**不进仓库、不进 Release**；发布版固件默认走合成回落，或由使用者自行放入本地采样。
- 本项目采用 **8k 采样**（约 10.4 KB）；若以后要更保真，换 16k 只需重新跑一次转换工具（宏与调用点不变）。
- 若要公开分发"带咳嗽采样"的固件：请换成自己录制/已授权（CC0 等）的咳嗽采样，再走同一转换流程。

**BP 机消息声**继续用合成（4 连响正弦 3200Hz）——实测原版就是纯音，合成与采样听感一致，没必要引入采样。

#### 6.8.3 优先级、去重与节流

- 优先级：**P0 审批/追问 > P1 结束/低电 > P2 操作反馈 > P3 连接音**。P0 到达时立即丢弃正在播放的低优先级音（总时长都很短，最多截断 1.5s）。
- 队列深度 2；高优先级可顶掉队列里的低优先级。
- 去重：同一会话同一事件 5s 内不重复；全局同一音型 3s 内不重复。
- 合并：2s 内多个会话完成 → **只响一次 BP 机声**，横幅显示"2 个会话已完成"（声音不叠加成噪音）。

#### 6.8.4 与录音/语音播放的互斥

- 音频外设是全局单例（`bsp_audio_set_format`），提示音与语音播放必须串行：统一由 alert 任务持有播放权。
- **录音期间不播提示音**（避免录进喇叭声）；唯一例外是审批/追问到达：按 C8 先停录丢弃，再响咳嗽。
- 语音识别完成/发送反馈属于 P2，若正处于下一次录音则延后到录音结束。

#### 6.8.5 音量、静音与免打扰

- 设备设置页「音量」0–100（0 = 静音，本地 NVS）；主机 `soundEnabled` 为总开关（唯一事实源，设备不持久化）。
- 桌面设置页提供**试听**按钮（`sound.test`），改完音量/音型可立即在设备上确认。
- 夜间免打扰（22:00–08:00 仅 P0 响）**待定**：DSH 当前不下发时间，需要先补时间同步（`config.time`），一期先不做。


### 12.2 与设计稿的偏差（均已实物验证/用户确认）

1. **固件 hello 的协议版本曾硬编码** `protocolVersion:1, capabilities:0`：主机因此永远按 v1 运行、
   设备收不到 `session.list`。已改为 `AP_PROTOCOL_VERSION` + 真实能力位（实测协商 `v2 / caps=127`）。
   这是设计稿未覆盖的实现缺陷，修复后写进本记录。
2. **列表超长标题**：设计稿写"省略号"；用户反馈后改为"选中行横向滚动完整显示、未选中行省略号"
   （8 行同时滚动在 C3 上明显卡顿）。会话页标题固定单行 + 横向循环滚动，修复折行挤占下方内容。
3. **单咳与双咳是两段独立采样**：实测 `approve-qq-once` 不是双咳的前缀，不能靠截断复用；
   固件同时链接 10.4KB + 4.7KB 两段采样（缺失时合成兜底）。
4. **8kHz 咳嗽采样 ↔ 16kHz 音型切换**会触发 ESP-IDF 一行无害 `i2s_channel_disable: channel has not been enabled`
   （BSP 已按"已停止"容忍，播放不受影响）；保留 8k（用户指定）以省一半 Flash。
5. **完成横幅**：暂用现有非模态 toast 呈现（标题 + 完成/出错/中断），设计稿的独立横幅样式留待后续细化。
6. **追问提示音**只在本批第一题响一次（`question.req` 是逐题下发，否则连续咳嗽）。
7. **采样版权**：`main/alert_cough_*.h` 由本地素材生成并加入 `.gitignore`，不随仓库分发；
   仓库/CI 构建自动回落到合成音，功能仍可用（音色不同）。
8. **插件首次部署**需在新克隆执行 `npm install`（BLE 桥依赖 `@stoprocent/noble`）；
   旧克隆的 `node_modules` 不能复用。安装后若桥子进程仍是旧进程，需重启 DSH 或结束 `bridge-worker.js`。
